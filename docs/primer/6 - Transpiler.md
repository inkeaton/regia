The Regia transpiler is a program whose role is to translate the regia source into executable code. In particular, it chooses a target language, first of all AgentSpeak (ASL). We wanna design it to be a multi-pass transpiler, and as such modular. In particular, some elements may be used without the rest, in order to integrate the transpiler with other applications, such as the Visual Editor.

We will describe how the current transpiler works, and also cite how we wanna change it. The first choice is the implementation language. The current transpiler is implemented in Python, using Lark as parser. #changes we would like to move to a compiled language, in order to reduce the dependencies of the tool, and the performance. Still, we would still like to rely on some libraries for the most complex elements, such as the parsing. The better alternatives are Rust and C++. Maybe the first would be better, be it more modern and with many quality of life features, such as memory management. Also, let's consider what could we do to remain on Python and iron out the cons.

The current transpiler starts with a preprocessing pass, in which imports are resolved, by uniting the files into a single file. also, comments are discarded, and documentation comments are preserved in a separate data structure. They would be added back into the program after AST construction. #changes it would be better to simply integrate documentation comments, and future compilation comments into the grammar

Afterwards, the program is parsed through Lark, creating a Concrete-Syntax-Tree (CST). This tree is then rewritten in to an Abstract-Syntax-Tree (AST), in order to simplify its processing. #changes We need to be able to export this CST. The idea is that if the visual editor shares that element, it would be very easy to edit the graph and the text of teh editro bidirectionally, preserving spaces and comments of the user. Also, we would need to be able to translate back the CST into text.

Having created the AST, it is then annotated with the previously removed comments, and then it is validated, checking for semantic errors. Lastly, it is emitted into the target language. #changes here we need to allow for multiple target languages. Moreover, we may insert another phase, instancing, in which, based on compilation comments, the transpiler may also produce some runtime files, such as .jcm files for instancing ASL agents.

Regarding error management, we have two main concerns. First, the error messages reported to the users must be as clean and understandable as possible, and if possible provide a hint on how to fix the error. All problems should be reported at once, to avoid a fix-compile-error cycle. The error format should be the same for each phase of the transpiler, and carry all needed information, position and similar. Such an error message should also be compatible with Monaco's error format.

We wanna have a clean structure. The CST and AST in particular should be as modular as possible, since the language may still vary, and it would be nice to be able to change only a section of the transpiler, instead of it all.

We will have lot's of automated tests, built alongside the transpiler.  Moreover, once the language and transpiler are mature enough, we will build a synthetic code generator, to create tunable regia code, and benchmark the performance, and see if we can find specific error cases

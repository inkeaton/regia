# The `.jcm` and Agent kinds in Jason

How Instancing (chapter 21) becomes a Jason Build's `.jcm`: the names and ports of the starting Agents, the top-level file of an Agent kind that plays several Roles, how `RANDOM` Propensity values are drawn, what the game is told about the starting cast, and what the Root Director knows about each kind so it can create joiners. Decided in the ticket *.jcm generation* (`.scratch/regia-2/issues/41-jcm-generation.md`). It builds on chapter 28's layout, chapter 30's Root Director, chapter 33's joins and chapter 35's seed and console filter, and implements the ASL mapping notes of chapter 21. It was checked against VEsNA-Pro's `vesna.jcm` and `VesnaAgent` (`vesna-pro-main/src/agt/vesna/VesnaAgent.java`), which read `temper`, `strategy`, `address` and `port` as user parameters.

The `.jcm` exists only when Instancing declares at least one Agent kind (chapter 21). Everything else in this chapter applies to that case.

## Starting Agent names

A kind with `COUNT n` gives starting Agents named **`<kind>_1` … `<kind>_n`**, with the kind's first letter lowercased like every Regia name in Jason (chapter 28).

- Always numbered, even for `COUNT 1`, so a name doesn't change when a count does. Behaviour cases rely on these names (chapter 35).
- Names can't collide. A kind's Agents are its name followed by `_` and digits, so kind `noble_1`'s first Agent is `noble_1_1`, which kind `noble` never makes. Kind names can't start with `regia_` or contain `__` (chapter 10), so they never meet Generated names.
- A name the game reports for a joiner (chapter 33) is the game's own and is checked there.

## Ports and addresses

Every VEsNA body is a WebSocket client that connects to the game at an `address` and `port` of its own. Jason's `instances:` can't give each copy its own port, so **every starting Agent gets its own `.jcm` entry**.

Two `TARGET JASON` keys (chapter 21) set the addresses:

| Key | Default | Meaning |
| --- | --- | --- |
| `address` | `localhost` | the game's host, for every body |
| `base_port` | `9080` (VEsNA-Pro's own default) | the Root Director's port; starting Agents take the next ones |

Ports are given in a **fixed order**:

1. the Root Director gets `base_port`;
2. the starting Agents get `base_port + 1`, `+ 2`, …, kinds **sorted by name**, then by number.

The order never depends on import order or on where a kind is declared, so overriding a count in another `.regin` moves only the ports after that kind. Joiners bring their own port (below).

## The `.jcm`

```
/* Generated by the Regia Transpiler <version> from banquet.regin. Do not edit. */
mas banquet {

    agent regia_director__royalBanquet : directors/RoyalBanquet.asl {
        ag-class:      regia.DirectorAgent
        address:       localhost
        port:          9080
        trace_console: all
    }

    agent drunk_noble_1 : roles/Drunkard__Guest.asl {
        ag-class:      regia.RegiaAgent
        temper:        temper(bravery(0.8))
        strategy:      most_similar
        address:       localhost
        port:          9081
        trace_console: all
    }

    agent noble_1 : roles/Guest.asl {
        ag-class:      regia.RegiaAgent
        temper:        temper(bravery(random(0.2, 0.6)), sympathy(0))
        strategy:      most_similar
        address:       localhost
        port:          9082
        trace_console: all
    }
    ...

    aslSourcePath: "asl";
}
```

- **`mas <entry>`**, with `asl/` as the ASL source path, so every include and file in the `.jcm` is relative to it (chapter 28).
- **The Root Director comes first**: `regia_director__<plot>` (chapter 31), running its Director file on `regia.DirectorAgent`. It is the only Director in the `.jcm`. Subplot Directors are created at runtime (chapter 31).
- **Then one entry per starting Agent**, in the port order above, on **`regia.RegiaAgent`**, `regia-jason`'s agent class that extends VEsNA-Pro's (chapter 28). Its file is the kind's top-level file (below).
- **User parameters**, all written out:
  - `temper` only when the kind gives some Propensity a value, written as chapter 14 says (`m(v)[mood]` for Moods), with `random(a, b)` left in for `RANDOM` (below). With no `temper`, VEsNA-Pro leaves the Agent without a Temper.
  - `strategy`, from the `JASON` group (default `most_similar`, chapter 21).
  - `address` and `port`.
  - `trace_console` (chapter 35), on every entry including the Root Director's.
- **No `goals:` and no `beliefs:`.** What the Infrastructure needs at start is in its own files: initial goals in `regia/agent.asl` and `regia/director.asl`, and the Root Director's `regia_start_cast`, `regia_rank_prefix` and `regia_kind` beliefs in its generated file.
- The header comment names the Transpiler version and the Entry, like every generated file (chapter 28).

## The top-level file of an Agent kind

A kind's Agents run one top-level ASL file:

- A kind that plays **one Role** runs that Role's file, `roles/<Role>.asl`, unchanged (chapter 28).
- A kind that plays **several Roles** runs a **combination file**, `roles/<RoleA>__<RoleB>[__…].asl`, with the Roles sorted by name. Designer names can't contain `__` (chapter 10), so it never meets a Role file. Kinds with the same Role set share one combination file.

A combination file is generated, like a Role file, and holds the **de-duplicated union** of its Roles' files:

```
/* Generated by the Regia Transpiler <version> from banquet.regia. Do not edit. */
{ include("regia/agent.asl") }
{ include("playbooks/Drinking.asl") }
{ include("playbooks/NobleSocializing.asl") }
regia_playbook(drinking).
regia_playbook(nobleSocializing).
regia_quota_watch(…).
// each Quota dispatcher once (chapter 33)
```

- **The Infrastructure once.** Jason doesn't skip a file included twice (chapter 28). Including the two Role files would run `regia/agent.asl`'s initial goals twice.
- **Each Playbook file once**, and each `regia_playbook` belief once (chapter 29). Two Roles can bring the same Playbook, directly or through Mappings to the same Subplot Role. Including it twice would double its plans.
- **Each Quota dispatcher and `regia_quota_watch` belief once** (chapter 33).

Role files stay as chapter 28 describes: one per Root Plot Role, including the ones no kind plays and those of a Build with no Instancing. Combination files exist only for the Role sets that kinds declare.

## Drawing `RANDOM`

`RANDOM(a, b)` is drawn **once per Agent, when it is created** (chapter 21), never by the Transpiler:

- The `temper` parameter carries the draw unevaluated: `bravery(random(0.2, 0.6))`.
- `regia.RegiaAgent` replaces each `random(a, b)` with a draw from [a, b] **before** handing the string to VEsNA-Pro's `Temper`, which only reads numbers.
- The draw uses the random source `regia-jason` seeds with the run's seed (chapter 35), so a behaviour case draws the same values every run.
- Starting Agents and joiners take the same path. A joiner's `temper` comes from its kind's `regia_kind` belief (below), so it gets its own draw.
- When an Agent has a `temper`, it writes one `cast` entry with the values it starts with, drawn or not: `TEMPER <agent> <propensity> <value> …` (chapter 34).

## What the game is told: `cast.json`

The game must open a body for each starting Agent and the Root Director, and the `.jcm` gives names and ports but not kinds. The Build writes a small manifest for the game next to the `.jcm`:

```
build/<entry>/cast.json
```

```json
{
  "address": "localhost",
  "director": { "name": "regia_director__royalBanquet", "port": 9080 },
  "agents": [
    { "name": "drunk_noble_1", "kind": "drunk_noble", "port": 9081 },
    { "name": "noble_1", "kind": "noble", "port": 9082 }
  ]
}
```

- Agents are listed in port order.
- It is written exactly when the `.jcm` is.
- It is for the game. How VEsNA and Godot read it is theirs. `ScriptedGame` keeps reading the `.jcm` (chapter 35).

## Agent kinds in the Root Director: `regia_kind`

A joiner arrives mid-run as a `regia_join` report (chapter 33), and the Root Director has to create its agent and add it to the cast. The `.jcm` can't help: Jason reads it only at launch, and a kind with no `COUNT` isn't in it. So the Root Director's file carries **one initial belief per declared kind**, including kinds with no `COUNT`:

```
regia_kind(noble, [guest], "roles/Guest.asl",
           [temper("temper(bravery(random(0.2, 0.6)), sympathy(0))"),
            strategy(most_similar), address(localhost), trace_console(all)]).
regia_kind(drunk_noble, [drunkard, guest], "roles/Drunkard__Guest.asl",
           [temper("temper(bravery(0.8))"),
            strategy(most_similar), address(localhost), trace_console(all)]).
```

| Argument | Meaning |
| --- | --- |
| `Kind` | the kind name, lowercased like any Regia name in Jason |
| `Roles` | the kind's Root Plot Roles as Jason names, in declaration order |
| `File` | the kind's top-level file, relative to `asl/` |
| `Settings` | the user parameters a `.jcm` entry of this kind gets, **without** `port` |

- `regia.spawn_agent(Kind, Name, Body)` (chapter 33) finds the kind's `regia_kind`, creates the agent on `regia.RegiaAgent` with `File`, passes each `Settings` entry as a user parameter, adds `port` from the report, and draws `RANDOM` as above.
- The join plan reads `Roles` for its `regia_cast` entries and `!regia_join(A, Roles)` (chapter 33).
- `Settings` is a list of `key(value)` terms, not fixed arguments, so a new `TARGET JASON` key adds an entry instead of changing the belief.
- This keeps chapter 28's rule: the Infrastructure's state is beliefs, and `regia-jason` keeps none of its own.

## The `regia_join` body fields

A join report carries exactly:

```json
{"type": "regia_join", "kind": "noble", "name": "noble_7", "port": 9107}
```

- `port` is required: a whole number in 1–65535, where the new agent's body connects.
- The address is always the `address` setting. A per-joiner address can be added if a game needs one.
- A missing or invalid `port` makes the report **nonsensical**: the Root Director ignores it and writes a Trace warning (chapter 33).

## Transpiler checks

### Errors

- A port past 65535: `base_port` plus the number of starting Agents is too large.
- `base_port` that isn't a whole number in 1–65535.

### Warnings

- An unknown key in the `JASON` group (chapter 21). The known keys are `strategy`, `address`, `base_port` and `trace_console`.

Codes are assigned by *Number the checks and add exemplar cases*.

# The `.jcm` and Agent kinds in Jason

How Instancing (chapter 21) becomes a Jason Build's `.jcm`: the names and ports of the starting Agents, the top-level file of an Agent that plays several Roles, how `RANDOM` Propensity values are drawn, what the game is told about the starting cast, and what the Root Director knows about each kind so it can create joiners. Decided in the ticket *.jcm generation* (`.scratch/regia-2/issues/41-jcm-generation.md`). Individual Agents and lowercase Target names were added in *Agent kinds and Instancing files* (`.scratch/regia-revision/issues/15-instancing.md`). The setup lines of kinds and individual Agents in *What a Staging runs when it starts* (`.scratch/showcase-1-5/issues/17-staging-start.md`). It builds on chapter 28's layout, chapter 30's Root Director, chapter 33's joins and chapter 35's seed and console filter, and implements the ASL mapping notes of chapter 21. It was checked against VEsNA-Pro's `vesna.jcm` and `VesnaAgent` (`vesna-pro-main/src/agt/vesna/VesnaAgent.java`), which read `temper`, `strategy`, `address` and `port` as user parameters.

The `.jcm` exists only when Instancing declares at least one Agent kind or individual Agent (chapter 21). Everything else in this chapter applies to that case.

## Starting Agent names

A kind with `COUNT n` gives starting Agents named **`<kind>_1` … `<kind>_n`**, with the kind's first letter lowercased like every Regia name in Jason (chapter 28). These are the names chapter 34 gives Agents in the Trace and in behaviour cases; the Jason agents and their bodies use them unchanged.

- Always numbered, even for `COUNT 1`, so a name doesn't change when a count does. Behaviour cases rely on these names (chapter 35).
- Names can't collide. A kind's Agents are its name followed by `_` and digits, so kind `noble_1`'s first Agent is `noble_1_1`, which kind `noble` never makes. Kind names can't start with `regia_` or contain `__` (chapter 10), so they never meet Generated names.
- An **individual Agent** (`AGENT percival …`, chapter 21) keeps its own name, first letter lowercased: `percival`. It is the name the game knows the character by.
- An individual Agent's name can't have the form `<kind>_<digits>` for a kind of the Build, whatever the kind's `COUNT`, so a count never makes two Agents share a name (`R3603`).
- A name the game reports for a joiner (chapter 33) is the game's own and is checked there.

## Ports and addresses

Every VEsNA body is a WebSocket client that connects to the game at an `address` and `port` of its own. Jason's `instances:` can't give each copy its own port, so **every starting Agent gets its own `.jcm` entry**.

Two `TARGET jason` keys (chapter 21) set the addresses:

| Key | Default | Meaning |
| --- | --- | --- |
| `address` | `localhost` | the game's host, for every body |
| `base_port` | `9080` (VEsNA-Pro's own default) | the game link's port; starting Agents take the next ones |

Ports are given in a **fixed order**:

1. the game link (chapter 28) gets `base_port`. No Director has a port of its own;
2. the individual Agents get `base_port + 1`, `+ 2`, …, **sorted by name**;
3. then the Agents of the kinds, kinds **sorted by name**, then by number.

The order never depends on import order or on where a kind is declared, so overriding a count in another `.regin` moves only the ports after that kind. Joiners bring their own port (below).

## The `.jcm`

```
/* Generated by the Regia Transpiler <version> from banquet.regin. Do not edit. */
mas banquet {

    platform: regia.GameLink("localhost", "9080")

    agent regia_director__royalBanquet : directors/RoyalBanquet.asl {
        ag-class:      regia.DirectorAgent
    }

    agent king : roles/Host.asl {
        ag-class:      regia.RegiaAgent
        temper:        temper(bravery(0.5), sympathy(0)[mood], aggressiveness(0)[mood])
        strategy:      most_similar
        address:       localhost
        port:          9081
    }

    agent percival : roles/Guard__Guest.asl {
        ag-class:      regia.RegiaAgent
        temper:        temper(bravery(0.8), sympathy(0.3)[mood], aggressiveness(0.1)[mood])
        strategy:      most_similar
        address:       localhost
        port:          9082
    }

    /* hothead_1, hothead_2, knight_1 */

    agent noble_1 : roles/Guest.asl {
        ag-class:      regia.RegiaAgent
        temper:        temper(bravery(random(0.2, 0.8)), sympathy(random(0, 0.8))[mood], aggressiveness(random(-0.4, 0.4))[mood])
        strategy:      most_similar
        address:       localhost
        port:          9086
    }

    /* noble_2 … noble_6, servant_1 … servant_3 */

    aslSourcePath: "asl";
}
```

- **`mas <entry>`**, with `asl/` as the ASL source path, so every include and file in the `.jcm` is relative to it (chapter 28).
- **The game link comes first**: a `platform:` line naming `regia.GameLink`, with the `address` and `base_port` settings as its two parameters (chapter 28). JaCaMo starts it before any agent.
- **Then the Root Director**: `regia_director__<plot>` (chapter 31), running its Director file on `regia.DirectorAgent`, with no `address` or `port`: Directors reach the game through the link. It is the only Director in the `.jcm`. Subplot Directors are created at runtime (chapter 31).
- **Then one entry per starting Agent**, in the port order above, on **`regia.RegiaAgent`**, `regia-jason`'s agent class that extends VEsNA-Pro's (chapter 28). Its file is the Agent's top-level file (below).
- **User parameters**, all written out:
  - `temper` only when chapter 14's emission rules call for it: a Playbook the Agent's Roles can be given names a Propensity in a Label or a `SHIFT`. It lists exactly those Propensities, written as chapter 14 says (`m(v)[mood]` for Moods), with the neutral value (0.5 for a Trait, 0 for a Mood) where the kind or the individual Agent gives none, and `random(a, b)` left in for `RANDOM` (below). With no `temper`, VEsNA-Pro leaves the Agent without a Temper. A Mood's value, drawn or not, lies in [-1, 1] and is written as it is, negative or not: the showcase's `aggressiveness(random(-0.4, 0.4))[mood]` (chapter 14, *ASL mapping notes*).
  - `strategy`, from the `jason` group (default `most_similar`, chapter 21), exactly when `temper` is written: VEsNA-Pro throws on a `temper` without it.
  - `address` and `port`.
- **No `goals:` and no `beliefs:`.** What the Infrastructure needs at start is in its own files: initial goals in `regia/agent.asl` and `regia/director.asl`, and the Root Director's `regia_start_cast`, `regia_rank_prefix` and `regia_kind` beliefs in its generated file.
- The header comment names the Transpiler version and the Entry, like every generated file (chapter 28).

## The top-level file of an Agent

An Agent runs one top-level ASL file, chosen by the Roles its kind (or, for an individual Agent, its declaration) gives it:

- An Agent that plays **one Role** runs that Role's file, `roles/<Role>.asl`, unchanged (chapter 28).
- An Agent that plays **several Roles** runs a **combination file**, `roles/<RoleA>__<RoleB>[__…].asl`, with the Roles sorted by name. Designer names can't contain `__` (chapter 10), so it never meets a Role file. Agents with the same Role set share one combination file.

A combination file is generated, like a Role file, and holds the **de-duplicated union** of its Roles' files. In the showcase, `knight_1` and `percival` play `Guest` and `Guard`, and run `roles/Guard__Guest.asl`:

```
/* Generated by the Regia Transpiler <version> from royal_banquet.regia. Do not edit. */
{ include("regia/agent.asl") }
{ include("unheard.asl") }
{ include("goals.asl") }
{ include("playbooks/Courtesy.asl") }
{ include("playbooks/Dining.asl") }
/* … Duelling, Keeping_watch, NobleSocializing, Scheming, Wagering */
regia_playbook(courtesy).
/* … one per included Playbook */
```

- **The Infrastructure once**, and `unheard.asl` and `goals.asl` once. Jason doesn't skip a file included twice (chapter 28). Including the two Role files would run `regia/agent.asl`'s initial goals twice.
- **Each Playbook file once**, and each `regia_playbook` belief once (chapter 29). Two Roles can bring the same Playbook, directly or through Mappings to the same Subplot Role, as `Guest` and `Guard` both bring `Courtesy`, `Duelling` and `Keeping_watch`. Including it twice would double its plans.
- **Each Quota dispatcher and `regia_quota_watch` belief once** (chapter 33).

Role files stay as chapter 28 describes: one per Root Plot Role, including the ones no kind plays and those of a Build with no cast. Combination files exist only for the Role sets that kinds and individual Agents end up with.

## Drawing `RANDOM`

`RANDOM(a, b)` is drawn **once per Agent, when it is created** (chapter 21), never by the Transpiler:

- The `temper` parameter carries the draw unevaluated: `bravery(random(0.2, 0.8))`.
- `regia.RegiaAgent` replaces each `random(a, b)` with a **decimal** draw from [a, b] (chapter 21, whatever the bounds look like) **before** handing the string to VEsNA-Pro's `Temper`, which only reads numbers.
- The draw uses the random source `regia-jason` seeds with the run's seed (chapter 35), so a behaviour case draws the same values every run.
- Starting Agents and joiners take the same path. A joiner's `temper` comes from its kind's `regia_kind` belief (below), so it gets its own draw.
- When an Agent has a `temper`, it writes one `cast` entry with the values it starts with, drawn or not: `TEMPER <agent> <propensity> <value> …` (chapter 34).

## What the game is told: `cast.json`

The game must serve the game link and a body for each starting Agent, and the `.jcm` gives names and ports but not kinds. The Build writes a small manifest for the game next to the `.jcm`:

```
build/<Entry path>/cast.json
```

```json
{
  "address": "localhost",
  "game_link": { "name": "regia_game_link", "port": 9080 },
  "agents": [
    { "name": "king", "port": 9081 },
    { "name": "percival", "port": 9082 },
    { "name": "hothead_1", "kind": "hothead", "port": 9083 },
    { "name": "hothead_2", "kind": "hothead", "port": 9084 },
    { "name": "knight_1", "kind": "knight", "port": 9085 },
    { "name": "noble_1", "kind": "noble", "port": 9086 },
    …
    { "name": "servant_3", "kind": "servant", "port": 9094 }
  ]
}
```

- `game_link` names the link as it appears in the envelope (chapter 28). No Director's name is in the manifest: the game never learns about Stagings.
- Agents are listed in port order.
- An individual Agent has no `kind`: the game knows it by its name, and can't spawn another.
- It is written exactly when the `.jcm` is.
- It is for the game. How VEsNA and Godot read it is theirs. `ScriptedGame` keeps reading the `.jcm` (chapter 35).

## Agent kinds in the Root Director: `regia_kind`

A joiner arrives mid-run as a `regia_join` report (chapter 33), and the Root Director has to create its agent and add it to the cast. The `.jcm` can't help: Jason reads it only at launch, and a kind with no `COUNT` isn't in it. So the Root Director's file carries **one initial belief per declared kind**, including kinds with no `COUNT` and excluding kinds removed with `NO KIND`:

```
regia_kind(noble, [guest], "roles/Guest.asl",
           [temper("temper(bravery(random(0.2, 0.8)), sympathy(random(0, 0.8))[mood], aggressiveness(random(-0.4, 0.4))[mood])"),
            strategy(most_similar), address(localhost)]).
regia_kind(knight, [guest, guard], "roles/Guard__Guest.asl",
           [temper("temper(bravery(0.8), sympathy(0.3)[mood], aggressiveness(0.1)[mood])"),
            strategy(most_similar), address(localhost)]).
/* … hothead, servant */
```

| Argument | Meaning |
| --- | --- |
| `Kind` | the kind name, lowercased like any Regia name in Jason |
| `Roles` | the kind's Root Plot Roles as Jason names, in declaration order |
| `File` | the kind's top-level file, relative to `asl/` |
| `Settings` | the user parameters a `.jcm` entry of this kind gets, **without** `port` |

- `regia.spawn_agent(Kind, Name, Body)` (chapter 33) finds the kind's `regia_kind`, creates the agent on `regia.RegiaAgent` with `File`, passes each `Settings` entry as a user parameter, adds `port` from the report, and draws `RANDOM` as above.
- The join plan reads `Roles` for its `regia_cast` entries and `!regia_join(A, Kind, Roles)` (chapter 33).
- `regia_kind` holds no setup lines: a line's `RANDOM` is rolled for each Agent, so the lines are a plan, `regia_instance_setup(kind(Kind), A)` (below).

## Setup lines of kinds and individual Agents

The Root Director's file carries one plan per kind and per individual Agent that has setup lines (chapter 21), `regia_instance_setup(kind(hothead), A)` or `regia_instance_setup(agent(percival), A)`, with a catch-all that does nothing. Chapter 30 (*Setup lines of kinds and individual Agents*) holds what the plan sends, and when `regia_begin` runs it.

- **`LIKE` is resolved by the Transpiler.** Each plan holds the lines the kind or Agent ends up with, its bases' lines in `LIKE` order and then its own (chapter 21). Nothing is inherited at runtime.
- In the showcase, only `hothead` has a plan (`LEARN grudge(percival, 2)`, `banquet.regin:19`). `AGENT percival, LIKE knight` takes `knight`'s lines, which are none.
- Which plan a starting Agent runs is the `Source` of its `regia_start_cast` entry (chapter 33). A joiner runs its kind's.
- `Settings` is a list of `key(value)` terms, not fixed arguments, so a new `TARGET jason` key adds an entry instead of changing the belief.
- This keeps chapter 28's rule: the Infrastructure's state is beliefs, and `regia-jason` keeps none of its own.

## The `regia_join` body fields

A join report carries exactly:

```json
{"type": "regia_join", "kind": "noble", "name": "noble_7", "port": 9107}
```

- `port` is required: a whole number in 1–65535, where the new agent's body connects.
- The address is always the `address` setting. A per-joiner address can be added if a game needs one.
- A missing or invalid `port` makes the report **nonsensical**: the Root Director ignores it and writes a Trace warning (chapter 33).

## Transpiler checks

**Errors**

- `R3601` A port past 65535: `base_port` plus the number of starting Agents is too large.
- `R3602` `base_port` that isn't a whole number in 1–65535.
- `R3603` An individual Agent named `<kind>_<digits>` for a kind of the Build.

An unknown key in the `jason` group, or a value outside the set its key takes, is chapter 21's `R2113`. The known keys are `strategy` (`most_similar` or `random`), `address` and `base_port`. The console level is not a setting: it is `regia run --console` (chapter 35).

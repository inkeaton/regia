# Map: Regia 2.0 design

Label: wayfinder:map

## Destination

A complete design spec for Regia 2.0. It covers the language (syntax, constructs, semantics), the instancing layer, the ASL mapping, and the architecture of the Transpiler and Visual Editor. It is written as docs (`GLOSSARY.md`, decision records in `docs/adr/`, spec chapters in `docs/spec/`), with every `#discuss` in `docs/primer/` either resolved or explicitly deferred, and is ready to hand to a separate effort that plans development.

## Notes

- Domain: language design for a BDI-based DSL aimed at game designers. Input is `docs/primer/` (frozen: superseded, never edited), plus the 1.0 code and docs in `1.0/` as a reference.
- Every grilling session calls the `grilling` and `domain-modeling` skills. Settled terms go straight into `GLOSSARY.md` (designer-facing names; BDI and ASL terms only as _Avoid_ aliases). Decision records only when a decision is hard to reverse, surprising, and a real trade-off.
- Readability rules for every syntax decision: as few symbols as possible, plain wording over BDI jargon, modular constructs (primer ch.1).
- Tickets: `.scratch/regia-2/issues/NN-<slug>.md`, with `Type:`, `Status:` and `Blocked by:` lines. The frontier is the open, unblocked, unclaimed tickets, lowest number first. Language core comes first.
- Plan, don't do: no code in this effort, only decisions and docs.
- Handoff constraint for the development effort: whoever writes the Transpiler is new to Rust, and the build is a learning experience. Tickets are cut small, Claude writes less code and sets exercises, using `vibe-wise:learn`, `mattpocock-skills:teach` and `scaffold-exercises` ([Implementation language for the Transpiler](issues/26-implementation-language.md)).

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [Research: dynamic plan loading in Jason](issues/23-research-jason-dynamic-plans.md): adding plans at runtime is possible, and source counting handles several Directors; filtering with a belief is simpler and keeps plan order. Nothing reads `priority` today; plan order decides. Input for the ASL mapping and the priority model.
- [Research: implementation language for the Transpiler](issues/25-research-implementation-language.md): Rust is strongest on lossless CST (rowan), WASM and single-binary distribution; C++ means more code by hand; Python struggles with WASM size and single-binary distribution. A Rust core with Python bindings is a sixth option. Input for [Implementation language for the Transpiler](issues/26-implementation-language.md).
- [Research: lossless syntax trees and round-tripping](issues/24-research-lossless-cst.md): lossless means tokens plus whitespace and comments reproduce the source exactly. A rowan/Roslyn-style tree has edit APIs; tree-sitter and Lezer mean patching text and reparsing. Indentation comes from a lexer with an indent stack. Open questions became [Bidirectional editing model](issues/27-bidirectional-editing-model.md).
- [Research: plan conflict resolution in BDI and game AI](issues/13-research-plan-conflict-resolution.md): "priority" is four decisions (event, plan, pre-emption, actions that can't run together). Jason only has source order and `[atomic]`, with `select__option/4` as a hook. JACK layers rank over order, GOAL has a first-vs-all switch, and game AI favours rank plus weight (dual utility). Input for [Priority model](issues/14-priority-model.md).
- [Research: grammar-driven parsing in Rust](issues/28-research-grammar-driven-parsing-rust.md): the lexer (indent stack, continuation, nested comments) is hand-written whatever we pick. lelwel fits best (resilient LL(1) generator from a grammar file, lossless tree, several errors per run, wasm playground) but has one maintainer and is pre-1.0. tree-sitter is mature but its lexing goes in C and it gives no messages. pest stops at the first error. The rust-analyzer approach is the fallback. Input for [Implementation language for the Transpiler](issues/26-implementation-language.md).
- [Statement and block syntax](issues/01-statement-and-block-syntax.md): indentation and explicit `.`/`;` mix freely; every header (`PLOT` too) ends with `:`; a body on the header's line is an Inline block ending at `;` or at the end of the line; `.` ends a Statement only before a space or the end of the line; Python indentation rules; `,`/`(` continue lines. Spec: `docs/spec/01-statements-and-blocks.md`.
- [Comment syntax](issues/02-comment-syntax.md): `#` / `#[ … ]#` (nestable) for plain comments, `#@key:` / `#@key[ … ]#` for doc comments, `#%` / `#%[ … ]#` reserved for Instancing comments; `## … ##` dropped. Doc comments are grammar nodes attached to the declaration directly below; open key set (`desc`, `author`, `version` known). Spec: `docs/spec/02-comments.md`.
- [Parameters and variables](issues/03-parameters-and-variables.md): every kind of Vocabulary item takes untyped parameters, Events included. A slot holds a Value or a Placeholder (`?name`): a blank filled by matching in the Trigger or Context, once per Plan run, never reassigned. Only what's certainly filled can be used. Which match is used is unspecified. Spec: `docs/spec/03-parameters-and-placeholders.md`, ADR 0001.
- [Numbers and arithmetic](issues/04-numbers-and-arithmetic.md): one Number kind; `< > <= >= =` and `+ - * /`; `RANDOM(a, b)` inclusive. The Context only tests (`=` compares); a Body names values with `?name = Expression.`, once and never reassigned. Non-Numbers make a Context comparison false and Body arithmetic fail the Plan. Spec: `docs/spec/04-numbers-and-expressions.md`, ADR 0002.
- [Goals and Trigger kinds](issues/05-goals-and-trigger-kinds.md): achievement Goals only, declared like Facts, reached when their Plan finishes; Events are momentary; Trigger kinds are `WHEN e:`, `WHEN f LEARNED/FORGOTTEN:`, `TO g:`, `WHEN g DROPPED:`; `WHEN` replaces `ON`; `FROM Role ?who` / `FROM DIRECTOR` on anything sent. Spec: `docs/spec/05-goals-and-triggers.md`, ADR 0003.
- [Context vs control flow](issues/06-context-vs-control-flow.md): `GIVEN` is the Context, a Block under the Trigger; several `GIVEN`s share a Trigger, first match in the text wins, optional `ELSE`, no prefix Statements. `IF`/`ELSE IF`/`ELSE` are Body Statements; their Placeholders live in their branch. `AND`/`OR` mixing needs parentheses. ASL: negate earlier siblings with fresh names. No loops. Spec: `docs/spec/06-context-and-control-flow.md`, ADR 0004.
- [Messaging between Agents](issues/08-messaging.md): `TELL <recipient> <fact or event>`, `ASK <recipient> TO <goal>`, `SIGNAL <event>` (to every Director giving the Playbook). Recipients are a filled Placeholder, a Role or `EVERYONE` (`BROADCAST` gone), never a named Agent. Messages only add; sending never waits. A told Fact is the receiver's own, with no source; `LEARNED FROM` fires only if new. Cooperation words reserved (`REFUSE`, `AGREED`/`REFUSED`/`REACHED`/`FAILED`, `TOLD`, trailing clauses). Spec: `docs/spec/07-messaging.md`.
- [Basic Action set](issues/07-basic-action-set.md): `LEARN`/`FORGET`/`CHANGE … TO` for Facts, `PURSUE`/`DROP` for Goals (named after their Trigger kinds), `TELL`/`ASK … TO`/`SIGNAL`, `PRINT(…)`, `WAIT`; only Custom Actions take `DO`. `PURSUE` waits, `, WITHOUT WAITING` carries on; `ASK` never waits. `DROP` stops the Plan and its waited-on sub-Goals. No-ops do nothing; arguments must be filled. Spec: `docs/spec/08-basic-actions.md`, ADR 0005.
- [Groups](issues/09-groups.md): no Groups in 2.0; random choice is a Body Block `EITHER:` … `OR:`, one Option runs, with optional relative `, WEIGHT <Expression>` (default 1; negatives count as 0 with a warning; all zero runs nothing and warns). Option Placeholders stay in their Option. "Any of a family" is a parameterised Fact. Spec: `docs/spec/09-random-choice.md`.
- [Scoping, imports and aliases](issues/10-scoping-and-imports.md): `IMPORT "path".` first in the file, relative, transitive, loaded once, cycles rejected, no export control. One flat namespace across the Program (the Entry files plus everything they reach). A name has one kind and one parameter count (ADR 0006), matching re-declarations merge, and declarations go in any order. `<external> AS <name>` on Facts, Events and Actions; dotted names are External names only. Local `FACT`/`GOAL` inside a Playbook or Plot are private, never sent, and kept but unseen when the Playbook is taken away. Spec: `docs/spec/10-scoping-and-imports.md`.
- [Plan failure and fallback](issues/11-plan-failure.md): a Plan fails at a Statement it can't carry out (including a reported Custom Action failure and `FAIL.`), stops, and undoes nothing. A failed recipe fails its Goal and every Body waiting on it, with no retry. A Goal with no applicable `TO` Plan fails; an unhandled Event is ignored. `WHEN g FAILED` notifies and doesn't rescue (ADR 0007). Every unreached Goal fires one of `DROPPED`/`FAILED`. Every failure leaves a trace entry; its format belongs to the Target. Spec: `docs/spec/11-failure.md`.
- [Time and timers](issues/12-time-and-timers.md): the language writes Durations (`<Expression> SECONDS`/`MINUTES`, unit always written) and the Target owns the clock (wall or game time, one per Program). 2.0 has only `WAIT <Duration>.`, which pauses its own Body; a non-Number Duration fails the Plan, a negative one counts as 0 with a warning. Timers, `EVERY`/`AFTER` Triggers and timeouts are out of scope. Spec: `docs/spec/12-time.md`.
- [Priority model](issues/14-priority-model.md): one Plan per Trigger on an Agent, ranked by precedence, then the Selection function (mood, only where allowed), then name with a warning. Precedence is written by whoever puts Playbooks together: a Plot's `PRECEDENCE:` Block (`OVER`, `TIES`, `SELF`, `PARENT`, `DURING …`) orders its Playbooks, Phases and Subplot subtrees; Instancing orders only independent Plots (none exist since [Instancing comments](issues/22-instancing-comments.md)). Defaults: first in the text, Subplot over parent, Phase over `DURING PLOT`. `PRIORITY` is removed. Spec: `docs/spec/13-plan-selection.md`, ADR 0008.
- [Label syntax and mood Labels](issues/15-label-syntax.md): Labels are `, KEYWORD …` after the Trigger, any order, `AND` inside one. A fixed set of two: `SUITS p AT n` (the only one that affects selection) and `SHIFTS m BY n`, literals in [-1, 1]. Propensities are declared as `TRAIT`/`MOOD` and get their values from Instancing. `SHIFTS` may also go on `GIVEN`/`ELSE`; no Labels on Director Plans. Suits alternatives replace mood alternatives, with no neutral one. Unsupported Labels: ignored, one warning. Spec: `docs/spec/14-labels.md`.
- [Roles inside Playbooks](issues/16-roles-in-playbooks.md): a Playbook declares its own Roles (`ROLE host.`), used only as `TELL`/`ASK` recipients and `FROM` Senders; it never directs another Agent. A Plot fills them with `, MAPPING <Plot Role> TO <Playbook Role>` on `ASSIGN` and `START SUBPLOT` (same names implicit, unfilled is an error). Each `ASSIGN` is a Giving; Roles are the union over Givings, checked live. `n OF` / `n PERCENT OF` pick Agents at random once, without overlap in one Statement, rounding down. Spec: `docs/spec/15-roles-and-mappings.md`.
- [Role setup](issues/17-role-setup.md): sugar for what each Agent of a Plot's Role starts with: `ROLE Guest STARTS WITH:` and a Block of `ASSIGN P[, MAPPING …]`, `LEARN f`, `PURSUE g`, as if told and asked by the Director. Runs per Agent per Staging, at Staging start before the initial Phase's entry Plans, and again for joiners; written order, failing Statements skipped. No counted picks. Its Playbooks are ordinary Givings (`UNASSIGN`, `PRECEDENCE`); Facts stay. Spec: `docs/spec/16-role-setup.md`.
- [Subplots and Stagings](issues/18-subplots-and-stagings.md): `START SUBPLOT` never waits and each run is a new, anonymous Staging; the cast is fixed at start; a Subplot outlives the Phase that started it. `END PLOT` stops its Body and ends every Subplot below it; `END PLOT WITH e` hands the parent an Outcome, heard as `WHEN P ENDED[, WITH e]` (first match). `END SUBPLOT P` ends the children silently. Start cycles are errors; no Plot parameters. Spec: `docs/spec/17-subplots.md`.
- [Conditions over a whole Role](issues/19-role-wide-conditions.md): Quota Triggers count different senders of one Event: `WHEN e FROM ALL Guest` / `FROM 3 OF Guest` / `FROM 50 PERCENT OF Guest`, on any Event Trigger, in Directors and Playbooks. Each Agent counts once; counts are kept per argument value against the live Role; `PERCENT` means at least that share. The count belongs to the Trigger while a Block with it is active, and resets after firing. It is its own Trigger, separate from the plain one. Only Events are counted, never other Agents' Facts. Spec: `docs/spec/18-quota-triggers.md`.
- [Cast changes mid-Plot](issues/20-cast-changes.md): only the game changes a Cast in 2.0: an Agent entering the Program joins the Root Plot (Roles from Instancing), one leaving leaves every Staging. Whole-Role Givings are standing and reach joiners after their Role setup; joiners never enter running Subplots. Leavers drop out of picks and quotas (checked again on leave); Messages to them are dropped with a trace. Directors hear `WHEN Guest [?who] JOINED/LEFT` and `WHEN Guest EMPTIED`; nothing automatic when a Role empties. Spec: `docs/spec/19-cast-changes.md`.
- [Director capabilities](issues/21-director-capabilities.md): a Director perceives the game, has its own per-Staging Facts but no Goals or Propensities, and directs Agents only with `ASK`/`TELL` (Sender `DIRECTOR`) and Director Statements; `Role DO` and `WORLD` are gone. `?who` can be a recipient, an `ASSIGN` target (not standing) or a `MAPPING`. Phases use `WHEN ENTERED:`/`WHEN EXITED:`; leaving a Phase silently stops its Plans, so `WAIT` works as a rough timeout; `TRANSITION` ends its Body and can re-enter. Failed Director Plans only leave a Trace. Spec: `docs/spec/20-directors.md`, ADR 0009.
- [Instancing comments](issues/22-instancing-comments.md): Instancing is optional, written as top-level `#%` in `.regia` files or in a `.regin` Instancing file (no markers); the importer overrides whole items, disagreeing siblings are an error. One Root Plot, inferred or `ROOT P.`; no independent Plots. `AGENT noble PLAYS Guest AND Drunkard:` with `COUNT n.` and `bravery AT RANDOM(a, b).`; the game spawns by kind. Target picked at build time; `TARGET JASON:` holds `key = value.` settings with defaults; `ASL_VERSION` retired. Spec: `docs/spec/21-instancing.md`.
- [Implementation language for the Transpiler](issues/26-implementation-language.md): Rust, with a WASM build for the editor (no server) and one native binary per platform; no Python bindings in 2.0. Hand-written lexer and recursive-descent parser building a lossless tree in the rust-analyzer style, with no parser generator (lelwel is a reference). The development effort is a learning effort for someone new to Rust. ADR 0010.

## Not yet specified

- **Match selection**: explicit ways to choose among a Context's matches (pick one at random, run for every match, rank by priority or by a value). Also forgetting or dropping everything that matches a blank (`FORGET hates(?x)` for every `?x`), counting matches in a Context (`GIVEN 3 OF hates(?x)`, spec 18), and the place for any looping construct, since 2.0 has no `WHILE`/`FOR`. Kept separate from precedence, which only ranks Plans ([Priority model](issues/14-priority-model.md)). Random choice among written Options is already `EITHER`/`OR` ([Groups](issues/09-groups.md)); a random-match form should read alongside it.
- **Sugar and math over Numbers**: a shorthand comparison on a one-slot Fact (`health < 20`), a small math library (`abs`, `round`, `min`, `max`), named Weight levels (`OFTEN`, `RARELY`) for `EITHER`/`OR`, and naming values in a Context (`?x = …`) if repeated Expressions hurt. Revisit once the core constructs are stable.
- **Richer Goals and Events**: Goals kept true (maintenance) or reached when a Fact holds (declarative); `FROM SELF`; renaming `EVENT` to `CUE` so "Event" can become the umbrella term. Revisit once the core constructs are stable.
- **Optional parameter types** (`param: type`): for Transpiler checks and Visual Editor hints. Not in 2.0's core. Revisit once the core constructs are stable.
- **The full ASL mapping**: how Playbooks are given and taken away at runtime (after the Jason research), shared infrastructure files instead of copying them into each file, what infrastructure state each agent holds (its Playbooks and which Plots gave them), logging of Agent actions for debugging and runtime verification (including the format, routing and runtime monitoring of the trace that failures and runtime warnings leave, spec 11), generating `.jcm` files, generated names for Local Vocabulary, and dropping local Goals when a Playbook is taken away (spec 10), Quota Trigger counts kept as generated Facts in the Director, from its Role records, and per-Giving in Agents (spec 18), and the precedence rank key: its encoding, how a Plot's position is computed when it is started from two parents, and `selectOption` comparing keys (spec 13). Also the per-Giving record of Role bindings and counted picks, and expanding Role recipients and `FROM Role` against it (spec 15). Running Role setups at Staging start and when an Agent joins, as Director messages (spec 16). The game reporting Agents joining and leaving, each Director's ordered record of standing Givings, and dropping sends to Agents that have left as trace entries (spec 19). A runtime identity per Staging carried in Givings and Signals, starting a Subplot's Director with its cast, and the children-first ending walk with its `ended` message to the parent (spec 17). The `.jcm` from Agent declarations, `RANDOM` Propensity values drawn by the infrastructure per Agent, the Root Plot's Director knowing each Agent kind's Roles and values for joiners, and combining Role files for an Agent kind playing several Roles (spec 21). Routing game percepts to the right Directors, dropping a Phase's running intentions on leaving it, running `EXITED` inside the atomic switch and `ENTERED` after it, and one-Agent Givings and Mappings (spec 20).
- **Supporting multiple Targets**: what is shared across Targets vs specific to each, and how Labels and instancing comments map per Target (Jason, plus the custom Python and C++ interpreters as config targets). Includes per-Target lowering of control flow (Jason's native `if` vs subgoal plans for the in-house interpreters, implied by the Target, spec 06), the set of Targets and the keys of their `TARGET` Instancing groups (spec 21), per-Target External names, and which clock a Target measures Durations with (wall or game time, spec 12). It depends on what each interpreter supports: suspending subgoals, `not` and `|` in contexts, failure propagation from a subgoal. See spec 06's ASL mapping notes.
- **Transpiler architecture**: the passes (preprocess, parse, CST, AST, validate, instance, emit), what is exposed as a library for the Visual Editor, and the error model (all errors at once, hints, one format across passes, Monaco-compatible). Rust with a hand-written parser is settled (ADR 0010); still open are the diagnostic type (miette or our own) and mapping hints to Monaco (`relatedInformation` or Hint markers), the Rust crate split (core, CLI, WASM), and import resolution behind an interface so the core does no file I/O. Depends on [Bidirectional editing model](issues/27-bidirectional-editing-model.md).
- **Visual Editor architecture**: the Transpiler running in-browser (WASM), a file system with folders and tabs, one tab per Plot, whether projects get import roots or search paths (2.0 only has relative paths, spec 10), and how `.regin` Instancing files and builds are shown and edited (spec 21); syntax highlighting (a Monaco Monarch grammar, semantic tokens from the WASM Transpiler, or tree-sitter).
- **What the graph shows**: which elements, toggling layers on and off, staying readable; how doc comments are shown or turned into generated documentation; which names a file uses through other files' imports (spec 10).
- **Testing strategy for the language spec**: how a spec chapter proves itself (examples, conformance cases). Not the development process.
- **Agent cooperation and undoing Messages**: a receiver refusing an `ASK` (`REFUSE`), replies to the asker as Goal kind words (`AGREED`, `REFUSED`, `REACHED`, `FAILED`), trailing clauses on message Statements (wait, timeout, expect reply), negotiation; Messages that make another Agent forget a Fact or drop a Goal; Fact provenance (`WHEN f TOLD FROM ?who`). The reserved reply `WHEN g FAILED FROM ?who` clashes with local `FAILED`, where `FROM` is the Goal's Sender (spec 11), so reply wording needs a redesign. Words reserved in spec 07. Also replies to a Director's `ASK`: in 2.0 a Director hears back only through Signals (spec 20). Post-2.0 unless the core needs it.
- **Running behaviours interfering**: several Playbooks reacting to one Trigger, in order or concurrently (the precedence proposal's `WITH`/`PARALLEL`, a generated dispatcher in Jason); pre-emption of a running Plan by a more important one; Actions that can't run together (`lock_doors` vs `open_doors`). 2.0 runs one Plan per Trigger and lets running Plans take turns (spec 13).
- **Precedence refinements**: layers (cross-cutting categories ordered once for the Program), naming single Trigger Blocks in relations, `TIES` between Plots, and knowing which Playbooks are given at the same time, so false "ordered by name only" warnings disappear and unordered competition could become an error (spec 13).
- **Richer Propensities**: a `SHIFT` Body Statement to change a Mood at a precise point (VEsNA-Pro has no Body-side mood change today); a ranking for unlabelled candidates defined by the language instead of the Target (needs a VEsNA-Pro scoring change); testing Propensities in a Context (`GIVEN aggressiveness > 0.5`); named value levels (`SUITS sympathy AT LOW`) alongside named Weight levels (spec 14). Moods on a Plot's Director (pacing, tension), which have none in 2.0 (spec 20).
- **Richer Mappings and Role tests**: filling a Role from several giving Roles, a separate random pick per receiving Agent (`TO EACH Guest`), counted recipients (`TELL 2 OF Guest`), and testing whether an Agent plays a Role (`GIVEN ?x PLAYS host`) (spec 15), a counted pick made per joining Agent in a Role setup (spec 16), and a Director moving Agents between Roles of a running Staging (`CAST ?who AS Host`, `UNCAST`; spec 19).
- **Richer Subplots**: Plot parameters (`PLOT HonorDuel(insult):`, which would also let Role setups use non-constant values, spec 16), a mid-run channel from child to parent (`SIGNAL PARENT e`), naming or ending one particular Staging among several, and recursive Subplots, which are a compile-time error in 2.0 (spec 17). Quotas over Subplot endings ("when every HonorDuel has ended"), which `ENDED` doesn't take in 2.0 (spec 18). Joiners of a parent Role carrying through to a running Subplot (spec 19).
- **Richer Directors**: Directors with Goals (`TO stage_ambush:` recipes, `PURSUE` in a Director, failure propagating inside a Director), a `STARTS WITH` for the Director's own Facts, and Directors reading Agents' state other than through Signals. 2.0 Directors are reactive state machines with Facts only (spec 20).

## Out of scope

- Development process, roadmap and milestones: the next effort, once this design is done.
- The custom Python and C++ interpreters, and VEsNA/Godot internals: we only design what Regia emits for them.
- The 1.0 demo game and the questionnaire pipeline.
- The synthetic code generator and benchmarks: tooling for after the Transpiler exists.
- Dialogue trees: a post-2.0 feature; core constructs must be stable first.
- Timers, repeating (`EVERY`) and delayed (`AFTER`, Phase timeouts) Triggers, and timeout clauses (`WITHIN`): post-2.0, ruled out in [Time and timers](issues/12-time-and-timers.md). 2.0 has only `WAIT`; repeating Events come from the game.
